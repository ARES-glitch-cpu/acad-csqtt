# CSQTT для Windows 10 x64

Минимальный клиент с нативным окном: сервер csqtt, пароль, хеши звонков VK и корпоративный HTTP-прокси с Basic-авторизацией. Поддерживает локальные **SOCKS5 `127.0.0.1:1080`** и **HTTP `127.0.0.1:8080`**, а также полноценный системный **IPv4 TUN**. Не требует Python на целевом компьютере. Прямой режим выбран по умолчанию: ядро подключается к TURN-узлам напрямую по TCP/443, не используя корпоративный HTTP-прокси. Сетевой NAT домашнего роутера или оператора мобильной связи не требует отдельной настройки.

## Быстрый запуск

1. Скачайте ZIP для Windows x64 из [Releases](https://github.com/ARES-glitch-cpu/acad-csqtt/releases/latest) и распакуйте **целиком** в отдельную папку.
2. Запустите **`CSQTT.exe`**. Папки `bin`, `_internal` и `assets` должны оставаться рядом.
3. Введите **адрес и порт вашего сервера csqtt**, **пароль пользователя csqtt**, **хеши VK** (до 6, можно полными ссылками `/call/join/`). Это не SSH-пароль и не пароль панели управления.
4. Корпоративный прокси: **`10.0.0.1:3128`**. Введите логин и пароль прокси в отдельные поля. Поддерживается **HTTP Basic**.
5. При необходимости нажмите **«Проверить прокси :443»**, затем **«Подключить»**. Результат проверки появится под кнопкой: зелёный — прокси доступен, красный — ошибка с пояснением. Проверка CONNECT без заданного TURN-хоста обращается к `dns.google:443` и проверяет только корпоративный прокси.
6. После получения конфигурации и готовности потока автоматически запускается выбранный режим и проверяется внешний IP. Для **TUN** запускайте `CSQTT.exe` от имени администратора; для **Прокси** повышение прав не нужно.
7. В режиме **Прокси** укажите локальный прокси в нужном приложении. В режиме **TUN** весь IPv4-трафик Windows идёт через CSQTT. Кнопка **«Отключить»** останавливает подключение и удаляет временные маршруты. Сворачивание и крестик убирают окно в трей, сохраняя подключение. Нажмите на значок, чтобы открыть окно; **«Выход»** в меню значка полностью закрывает приложение и оба дочерних процесса.

В боковой панели доступны **«Туннель»**, **«Опции»** и **«Журнал»**. В «Опциях» выберите режим: **Прокси** (SOCKS5/HTTP) или **TUN** (системный IPv4 через Wintun). Кнопки подключения и состояние видны на всех экранах. Адреса локальных прокси можно скопировать, пароли — временно показать кнопкой рядом с полем.

Для диагностики откройте **«Журнал»**, нажмите **«Скопировать журнал»** или **«Сохранить…»** для экспорта в UTF-8 `.txt`. Также работают Ctrl+A → Ctrl+C и меню правой кнопки мыши. Экспортируется тот же текст с замаскированными паролями и хешами, который показан в окне.

**Firefox:** Настройки → Настройки сети → ручная настройка → SOCKS `127.0.0.1`, порт `1080`, SOCKS v5; включить DNS через SOCKS v5. Альтернатива: HTTP-прокси `127.0.0.1:8080`, использовать также для HTTPS.

Проверка из PowerShell/командной строки:

```powershell
curl.exe --proxy socks5h://127.0.0.1:1080 https://api.ipify.org
curl.exe --proxy http://127.0.0.1:8080 https://api.ipify.org
```

В режиме **Прокси** системные настройки Windows не меняются: через CSQTT идут приложения, явно использующие локальный SOCKS5/HTTP. SOCKS поддерживает TCP CONNECT; UDP ASSOCIATE не реализован. В режиме **TUN** Windows направляет IPv4-трафик через Wintun и CSQTT; требуется запустить клиент от имени администратора. IPv6 пока не перенаправляется и может идти напрямую — для защиты от утечки IPv6 отключите IPv6 на активном физическом подключении на время TUN-сеанса. При штатном отключении клиент удаляет маршруты и сбрасывает DNS/адрес адаптера; состояние аварийного сеанса проверяется при следующем запуске. В portable-пакет включается официальный `wintun.dll` (Wintun 0.14.1) и файл лицензии; сборка проверяет SHA-256 архива перед включением. Для режима TUN нужен доступ к драйверу Wintun в составе пакета.

## Как устроено подключение

В режиме **Прокси**:

```text
Приложение → SOCKS5 / HTTP на 127.0.0.1
           → пользовательский TCP/IP-стек
           → локальный UDP с IP-пакетами, только 127.0.0.1
           → ядро CSQTT
           → TCP к корпоративному HTTP-прокси 10.0.0.1:3128
           → CONNECT <TURN-хост>:443 с авторизацией
           → TURN по TCP или TLS в зависимости от URI VK
           → ваш сервер csqtt → интернет
```

**С компьютера наружу транспорт — TCP через корпоративный прокси.** Локальный UDP между двумя процессами не выходит за пределы компьютера. Участок TURN → сервер работает по протоколу csqtt; корпоративный прокси его не видит.

Порт `443` фиксируется **для TURN**, а не для адреса вашего сервера csqtt. В поле сервера нужно вводить реальный порт из его настроек. Порт корпоративного HTTP-прокси остаётся `3128`.

Ядро дополнено HTTP CONNECT перед TURN/TCP/TLS. Запросы API VK и получение первоначального DNS через HTTPS также направляются через этот прокси. При недоступности прокси перехода на прямое подключение или TURN/UDP нет. DNS внутри пользовательского TCP/IP-стека передаётся в туннеле к DNS, полученному от сервера.

В режиме **TUN** путь системного IPv4-трафика: `Windows IPv4 → Wintun → локальный UDP-порт → ядро CSQTT → TURN/сервер`. Отдельный маршрут `/32` сохраняет корпоративный прокси на физическом интерфейсе, чтобы транспорт не попадал обратно в туннель.

Публичный API DNS `dns.google:443` используется только ядром при необходимости разрешить доменное имя до установления туннеля. Домен сервера и TURN должен разрешаться в IPv4. Обычный NekoBox не реализует протокол csqtt, поэтому здесь используется исходное ядро csqtt и отдельный пользовательский TCP/IP-стек.

## Дополнительные параметры

- **TURN-хост:** необязательный IPv4/домен без схемы и порта. Пустое поле использует адреса из ответа VK. Переопределение имеет смысл только для TURN-сервера, принимающего выданные VK учётные данные и TCP на 443. Указывать здесь обычный VPS csqtt нельзя.
- **Workers:** по умолчанию 6; можно увеличить после успешного подключения.
- **Обфускация:** `unified` по умолчанию; должна соответствовать серверу.
- **SRTP:** `auto` по умолчанию, также доступны `wrap` и `dtls`. Внутренний DTLS в csqtt не меняет внешний транспорт TCP.
- **Поколение / Salt:** заполните, если они выданы сервером; иначе `0` и пустое значение.
- **Запомнить профиль:** все поля сохраняются в `%LOCALAPPDATA%\CSQTT\profile.dat`, зашифрованном Windows DPAPI для текущего пользователя. В portable-архив профиль не включается. Профиль версии 1.3.1 и старше загружается автоматически; при следующем сохранении переносится в новую папку. При снятой галочке и следующем подключении сохранённый профиль удаляется.

Пароли передаются ядру в окружении дочернего процесса, а не в аргументах запуска. Журнал существует в памяти окна; пароли и полные/короткие хеши маскируются. Учётные данные не вшиты в исходники или исполняемый файл.

## Если подключения нет

- **407:** неверные логин/пароль либо прокси требует NTLM/Kerberos. Эта версия поддерживает Basic. Ошибка 407 может появиться и при обращении API VK через прокси.
- **403 / CONNECT rejected:** прокси запрещает конкретный TURN/API/DNS-хост или порт. Разрешённый порт 443 сам по себе не гарантирует доступ к любому хосту или протоколу на нём.
- **TURN connect / allocation:** выбранный TURN должен действительно обслуживать TCP/TLS на 443. Произвольный UDP TURN нельзя превратить в TCP простым изменением порта.
- **Ошибки VK / CAPTCHA:** хеш может быть недействителен, звонок завершён, API ограничен или нужна капча. Используется автоматическая авторизация исходного ядра; Android WebView и ручное решение капчи в этой оболочке не реализованы.
- **Нет TUNCONF / READY:** проверьте адрес сервера, пароль csqtt, обфускацию, поколение/Salt и журнал ядра. Наличие открытого локального порта ещё не означает рабочий интернет.
- **После смены числа потоков остаётся прежнее количество, «превышен лимит потоков»:** сервер может хранить число от предыдущего подключения. В этой сборке каждый успешно подключившийся поток отправляет `GETWORKERS` с новым числом: согласование больше не зависит от единственного потока, который сам мог быть отклонён по старому значению. В строке `TUNWORKERS` указаны согласованное число и лимит сервера; `лимит сервера 0` означает отсутствие заданного лимита. Если сервер сообщает ненулевой лимит, увеличить его можно в настройках пользователя/группы на сервере.
- **Порт занят:** выберите другие разные локальные порты; слушатели привязаны только к loopback.

## Сборка и проверки

Исходники приложения — `csqtt_client/`; помощник SOCKS/HTTP и IP-стек — `packet-proxy/`; адаптированное ядро — `core/rust-client/`. Исходная база взята из предоставленного архива `csqtt-2.5.0.7z`. Готовый `client.exe` из архива не используется: ядро пересобирается из исходников.

Структура проекта:

```text
main.py                      запуск приложения
csqtt_client/
  application.py             события интерфейса и управление процессами
  config.py                  версия и пути
  models/                    профиль и проверка параметров
  services/                  HTTP CONNECT и запуск ядра
  platform/windows/          оформление окна, трей и Windows DPAPI
  ui/                        страницы, виджеты, цвета и стили
assets/                      иконки и шрифты
scripts/                     сборка, подготовка иконки и сбор лицензий
tests/                       проверки оболочки
core/                        исходники ядра CSQTT
packet-proxy/                локальный SOCKS5/HTTP-прокси
```

Для запуска из исходников: `python -m csqtt_client`. Сборка по-прежнему вызывается через `build.ps1` в корне.

Нужны Windows x64, Python 3.14 + PyInstaller, Go 1.27, Rust 1.97.1 и MSVC Build Tools. При наличии `.tools/cargo` и `.tools/rustup` скрипт использует локальный Rust.

```powershell
powershell -ExecutionPolicy Bypass -File .\build.ps1
python -m unittest discover -s tests -v
cd packet-proxy
go test -v ./...
```

Номер приложения берётся из `VERSION`. Push соответствующего тега (например, `1.3.2` → `v1.3.2`) запускает GitHub Actions: сборку Windows x64, короткую проверку запуска и публикацию ZIP со всеми зависимостями и SHA256 в Releases. Пример имени архива: `CSQTT-v1.3.2-Win10-x64.zip`. На обычные коммиты сборка релиза не запускается; полные тестовые наборы в релизный процесс не включены.

Тесты проверяют CONNECT с Basic, ошибки авторизации, DPAPI, фиксированный TCP/443, SOCKS и HTTP через два связанных пользовательских IP-стека, обработку данных сразу после CONNECT и отказ UDP ASSOCIATE. Регрессионные тесты ядра `worker_negotiation_tests` проверяют смену 6 → 12, 6 → 18 и 12 → 6 потоков через локальный TCP TURN-сервер, а также ответ с заданным серверным лимитом. Они не заменяют проверку с реальным сервером csqtt и корпоративным прокси.

## Linux (Ubuntu/Debian x86_64)

Linux-сборка публикуется отдельно в виде архива `CSQTT-v*-Linux-x86_64.tar.gz`.

1. Распакуйте архив: `tar -xzf CSQTT-v*-Linux-x86_64.tar.gz`.
2. Запустите `./CSQTT/CSQTT` из графического сеанса. Для режима **Прокси** права root не нужны.
3. В режиме **TUN** приложение запросит системное подтверждение polkit. Нужны `/dev/net/tun`, `iproute2` и работающий `systemd-resolved`. Помощник создаёт интерфейс `csqtt0`, передаёт его файловый дескриптор существующему Rust-ядру через Unix socket, направляет IPv4-маршруты и DNS через TUN, оставляя корпоративный прокси на физическом интерфейсе.
4. При штатном отключении или завершении GUI помощник очищает временные маршруты, DNS-настройки и интерфейс. Если процесс завершился аварийно, следующий запрос TUN пытается восстановить сохранённое состояние из `/run/csqtt/tun-state.json`.
5. IPv6 через этот TUN не перенаправляется. Более специфичные маршруты локальных сетей могут оставаться вне туннеля. Не запускайте одновременно два системных VPN/TUN.

На Linux профиль хранится в `~/.config/CSQTT/profile.json` с правами каталога `0700` и файла `0600`. Это ограничение доступа текущим пользователем, а не шифрование; в Windows для профиля по-прежнему используется DPAPI.
## Прямое подключение без корпоративного прокси

На странице подключения в блоке «Доступ в интернет» оставьте **«Напрямую (Wi-Fi / мобильный интернет)»**. Поля корпоративного прокси будут отключены; клиент не передаёт `CSQTT_HTTP_PROXY` и реквизиты прокси в Rust-ядро. Прямой путь использует TCP к TURN-адресам, выданным сервером, на порту 443. Он работает через обычное домашнее подключение или мобильную точку доступа, если сеть разрешает исходящие TCP-соединения к этим адресам.

Для корпоративной сети, где прямой доступ закрыт, переключите вариант на **«Через HTTP-прокси»** и заполните адрес/учётные данные. Этот режим сохраняется как совместимый вариант.

При выборе системного TUN клиент сохраняет физические маршруты к фактическим TURN-узлам (или к корпоративному HTTP-прокси), чтобы управление туннелем не зацикливалось внутри самого TUN.
